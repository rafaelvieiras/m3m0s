# Memory schema — technical detail of A3/D9

This document operationalizes decision **D9** (see
[`docs/decisions/`](./decisions/README.md)) — the 4 axes
`domain`/`source`/`agent`/`tags+metadata` — against the real storage
implementation. Up to D28 the backend was
[chromem-go](https://github.com/philippgille/chromem-go); since D28 it is
**SQLite** (`internal/sqlstore`, pure-Go driver `modernc.org/sqlite`, schema
versioned by `goose` migrations) — the `entries` table now has a dedicated
column per D9 field instead of a flattened `map[string]string`, and the
`domain`/`domain_category`/`source`/`agent`/`tags` filters run over the
in-memory index of `internal/store.MemoryStore` (reloaded from SQLite at
boot), no longer against a vector-query `where`. `metadata_json` remains the
only truly free field — a direct round-trip of `schema.Entry.Metadata`
(`json.Marshal`), including the reserved keys of D12/D15/D21/D22
(`source_content_ref`/`related_to`/`valid_until`/`pinned`/`access_count`/
`last_accessed_at`).

## Field table

| Field (conceptual, D9) | Column in the `entries` table (SQLite, D28) | Format | Required | Filter |
|---|---|---|---|---|
| `domain` | `domain` | `<category>:<instance>`, regex `^[a-z0-9_]+:[a-z0-9._-]+$` | Yes | Restricts the candidate set BEFORE the similarity computation (`scoreDomainCandidates`) |
| — | `domain_category` *(derived, see below)* | only the part before the `:` | Yes (auto) | Go post-filter over the already-scored candidates |
| `source` | `source` | free string, suggested list below | Yes | Go post-filter |
| `agent` | `agent` | free string, `NULL` column | No — **`NULL` column** when there is no named agent (do not store `""`) | Go post-filter, only when present |
| `tags` | `tags_json` | JSON array (`["tag1","tag2"]`) | No | Go post-filter (`matchesTags`) — never native, neither in chromem-go nor in SQLite |
| `metadata` | `metadata_json` | JSON serialized as a string (`json.Marshal`) | No | Never used in a filter — only decoded back in the response |
| *(existing, kept)* | `content` | plain text | Yes | Not a filter — it is the text embedded for semantic search |
| *(existing, kept)* | `created_at`, `updated_at` | RFC3339Nano | Yes (auto) | `created_at` orders `/recent`; no equality filter |
| *(new, D28)* | `embedding` | `BLOB`, float32 little-endian | Yes (auto) | Never filtered — only used for the cosine computation in `internal/store/similarity.go` |
| *(existing, ID)* | `id` (PK) | `mem_<nanoid>` — or `chunk_<nanoid>` when the memory comes from `m3m0s watch` (Phase 2, D11) reindexing a piece of a file | Yes (auto) | — |
| *(watch, Phase 2)* | `metadata.file_path` (inside `metadata_json`) | path relative to the watched root, e.g. `"docs/decisions/README.md"` | Only on memories generated by `watch` | Go post-filter over the decoded `metadata_json` (`DeleteByFilePath`) |
| *(watch, Phase 2)* | `metadata.heading` (inside `metadata_json`) | text of the section's Markdown header, absent if the chunk is the whole file | No | No |

> Note: the domain category names `codigo` (code) and `pessoal` (personal) are
> stored values kept as-is for compatibility with existing data (Portuguese for
> "code" / "personal"). The examples below use them verbatim.

### Why `domain_category` exists separately from `domain`

Historically (chromem-go, up to D28) this column existed because the `where`
of `Query()` only did exact per-key equality, with no prefix/`LIKE` support —
"everything that is code, no matter the repo" could not be expressed by
filtering `domain LIKE 'codigo:%'` without scanning the whole collection. With
SQLite (D28) that limitation itself no longer exists (`WHERE domain LIKE
'codigo:%'` would be trivial in plain SQL) — but the `domain_category` column
was kept anyway: the in-memory index of `internal/store` already does this
filter in Go over `schema.Entry.DomainCategory` (a first-class field since
D9), so recomputing the prefix every time from `domain` would bring no real
gain at this scale, and keeping the column avoids reopening the
`schema.Entry` contract for no reason. It is still an **implementation
detail, not a 5th product decision**.

### Suggested list (not closed in code) for `source`

`claude-code`, `opencode`, `openwebui`, `github-scrape`, `linkedin-scrape`,
`twitter-scrape`, `cli`, `manual`, `watch` (when the entry comes from
`m3m0s watch` reindexing a changed file, not from an active agent tool call).
New values do not require a schema migration — it is a free string.

### Why `tags`/`metadata` still have no native filter even after SQLite

Unlike `domain_category`, which only existed because of chromem-go's
limitation, `tags`/`metadata` never depended on it — even with plain SQL
available (D28), filtering a JSON array (`tags_json`) or free keys inside
`metadata_json` would require SQLite JSON functions (`json_each`,
`json_extract`) scattered across the queries, for a gain that does not pay off
at m3m0s's personal scale (hundreds to a few thousand entries). The m3m0s core
solves this the same way as before: semantic search by domain (which already
restricts the set strongly) followed by a Go filter (`matchesTags`) over the
already-decoded `tags` of the candidates.

## Concrete examples (covering the described multi-tool scenario)

**A book being written via Claude Code:**
```json
{
  "domain": "writing:practical-ai-book",
  "domain_category": "writing",
  "source": "claude-code",
  "tags_json": "[\"chapter-3\",\"draft\"]"
}
```

**The same book discussed later via Open WebUI** (same `domain`, different
`source` — this is what allows joining the two in a search by `domain`):
```json
{
  "domain": "writing:practical-ai-book",
  "domain_category": "writing",
  "source": "openwebui",
  "metadata_json": "{\"conversation_id\":\"conv_8f2a\",\"openwebui_project\":\"Books\"}"
}
```

**A React project via Claude Code:**
```json
{
  "domain": "codigo:my-react-app",
  "domain_category": "codigo",
  "source": "claude-code"
}
```

**An external agent scraping the user's LinkedIn** (a named agent crossing a
domain that is neither code nor writing — `agent` is what ties this to that
agent regardless of the `domain`):
```json
{
  "domain": "pessoal:social-media",
  "domain_category": "pessoal",
  "source": "linkedin-scrape",
  "agent": "my-agent"
}
```

## Supported vs. unsupported search patterns (D28)

| Search | How |
|---|---|
| "Everything in the exact domain `codigo:m3m0s`" | `Filter.Domain` — restricts the candidate set before the cosine computation (`scoreDomainCandidates`) |
| "Everything that is code, any repo" | `Filter.DomainCategory` — Go post-filter over the domain's candidates |
| "Everything a given agent touched" | `Filter.Agent` — Go post-filter |
| "Everything coming from Open WebUI" | `Filter.Source` — Go post-filter |
| "Domain + source combined" | Both filters applied in sequence (implicit AND) |
| "By tag" | `Filter.Tags` — Go post-filter (`matchesTags`), never native |
| "By field inside `metadata_json`" | Decode and check in Go after already having the results — never native |

## Out of scope of this spec (left for the Phase 1 implementation)

- Whether `domain_category` is validated against a closed list in code, or
  stays only a documented convention (free, no enforcement).
- Migration of the data already in the current `memory-server` (which only has
  `project`, with no `domain`/`source`/`agent`) — needs a backfill rule when
  Phase 1 ports the real data.
- Final indexing/dedup format (already foreseen in the plan: "pre-insert
  dedup" and "formatted context block") using these new fields.
