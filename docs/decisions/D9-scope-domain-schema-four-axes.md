# D9 — `scope`/`domain` schema: 4 orthogonal axes

**Status:** Accepted

**Context:** the previous system used `project` = basename of the cwd (collides between same-named folders on different machines, and does not work for non-code domains). The original draft of A3 (a free `domain` with a prefix such as `codigo:<repo>`) implicitly assumed that "what the memory is about" and "who/what generated the memory" were the same thing. They are not: the maintainer uses multiple tools/agents (Claude Code, OpenCode, Open WebUI, a persistent named agent) that **share the same content domains** (e.g. the same book in Markdown can be written via Claude Code and discussed via Open WebUI) and, at the same time, **one tool/agent can cross several domains** (a named agent may touch the book, code and data scraped from LinkedIn/Twitter/GitHub in the same session). A single hierarchical field cannot represent two independent axes that intersect.

**Decision:** a schema with 4 fields:
- `domain` — what the memory is about, stable regardless of who wrote it. Free string with a prefix convention per macro-category: `codigo:<repo>`, `escrita:<projeto>`, `pessoal:<area>`, `cliente:<nome>`. (The prefixes are stored data values and are kept in Portuguese for compatibility: `codigo` = code, `escrita` = writing, `pessoal` = personal, `cliente` = client.)
- `source` — which tool/technical interface generated the record: `claude-code`, `opencode`, `openwebui`, `github-scrape`, `linkedin-scrape`, `cli`, `manual`, etc. (an extensible enum, not closed in code).
- `agent` (optional, `null` in most cases) — the name of the named, persistent logical agent when it is an entity distinct from the underlying technical tool (e.g. `helper`, which may operate via the Claude Code CLI but is the user's own identity, not the tool's).
- `tags` (free array) + `metadata` (free JSON) — extra granularity specific to each source (book chapter, Open WebUI `conversation_id`, GitHub scrape commit sha).

**Why:** it allows two orthogonal kinds of search without collision — "everything about domain X, regardless of origin" (`domain=escrita:my-book`) and "everything agent Y touched, regardless of domain" (`agent=helper`). It follows the same "essential typed fields + free metadata + tags" principle as getengram.app ([D6](D6-getengram-analysis.md), item 6), adding `source`/`agent` as an axis that the original A3 draft did not cover. The exact types (closed enum vs. free string for `source`, format validation for `domain`) are left to the Phase 1 implementation design — what is closed here is the shape of the axes, not the data type of each. **Full technical detail** (mapping of these 4 axes onto chromem-go's `map[string]string`, including the derived `domain_category` field needed because chromem's `where` only does exact equality, with no prefix matching) is in **[docs/memory-schema.md](../memory-schema.md)**.
