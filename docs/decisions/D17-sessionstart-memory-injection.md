# D17 — Automatic memory injection via `SessionStart` (closes the "read" side left pending by Phase 8/D14)

**Status:** Accepted

**Context:** [D14](D14-claude-code-hook-auto-capture.md) (Phase 8) solved the "write" side of auto-capture — `PreCompact`/`SessionEnd` send what happened in the session to m3m0s. But the project's original goal (`AGENTS.md`, "Why it exists") is to reduce tokens spent **rediscovering** context — that requires the "read" side: the tool pulling relevant memory by itself, without the model having to decide to call a search tool. The maintainer asked for this design on 16 Jul 2026 after seeing, in practice, the `claude-mem` plugin doing exactly that via a `SessionStart` hook that injects a condensed digest at the start of the session.

**Decision, in 3 parts (closed with the maintainer before coding, same discipline as [D11](D11-watch-mechanism.md)/[D12](D12-llm-fact-extraction.md)/[D14](D14-claude-code-hook-auto-capture.md)):**
1. **The same `m3m0s hook claude-code` subcommand, no new CLI.** `Run` (`internal/hook/hook.go`) already reads `payload.hook_event_name` — it now dispatches to `RunSessionStart` when the value is `"SessionStart"`, and follows the [D14](D14-claude-code-hook-auto-capture.md) capture path in any other case. Zero additional registration/subcommand.
2. **Data source: `GET /api/v1/recent?domain=<domain>&limit=15`**, not `search` — at the moment `SessionStart` fires there is no user query yet to search by similarity, so the only thing that makes sense is "what is recent in this domain". `domain` uses the same `codigo:<basename(cwd)>` inference as [D14](D14-claude-code-hook-auto-capture.md) item 4 (`hookDomainFromCwd`), without duplicating code. Formatting reuses `apitypes.BuildContextBlock` (which already existed for `/search`) — the only adjustment made to it was omitting the `[0.00]` prefix when `Score` is nil (the `Recent` case, which does not score by similarity; showing "0.00" would suggest "irrelevant" when it really is just "not scored" — this fixes a small cosmetic defect that already existed in the `/search` usage too).
3. **Filter by the payload's `source`: only inject on `"startup"` and `"clear"`.** `SessionStart` carries a `source` field with 4 possible values (`startup`/`resume`/`clear`/`compact`). `resume` already carries the full history of the previous session and `compact` already has the summary that Claude Code itself just generated — injecting in those two cases would be redundant at best. `startup`/`clear` are the genuinely "blank" session cases, where the token savings are real. The choice was confirmed with the maintainer via a direct question (the "always inject" alternative was discarded on purpose).

**Mechanism:** `RunSessionStart` (`internal/hook/sessionstart.go`) resolves credentials (the same `ResolveCredentials` as [D14](D14-claude-code-hook-auto-capture.md)), fetches `Recent` with `context.WithTimeout(ctx, 5s)` — **not** the 30s default of `client.New` — and, if there is at least 1 result, writes to stdout the JSON `{"hookSpecificOutput": {"hookEventName": "SessionStart", "additionalContext": "<ContextBlock>"}}`, the officially documented Claude Code contract for this event. Any failure at any step (no credentials, server down, timeout, 0 results) exits silently without writing anything to stdout — it never hangs nor "seems to fail" the session (the same spirit as [D14](D14-claude-code-hook-auto-capture.md) item 1, now in both directions). Registered in `~/.claude/settings.json` as a 3rd hook entry, next to `PreCompact`/`SessionEnd` ([D14](D14-claude-code-hook-auto-capture.md)) — **without** `"async": true`: it was confirmed that asynchronous hooks cannot inject `additionalContext` (they only run after the session has already started), so this one must be synchronous.

**Accepted risk, different from [D14](D14-claude-code-hook-auto-capture.md)'s risk:** this hook is synchronous and blocks the start of **every** Claude Code session, in **every** project (not just those that use m3m0s) — if the server is down or slow, every `claude` the maintainer opens waits until the timeout. Mitigated with a 5s context ceiling specific to this call (much shorter than the 30s of the generic client, used in the other asynchronous/CLI paths where waiting bothers nobody) — in the worst case, the session opens without extra context instead of hanging, but there is still a window of up to 5s of noticeable delay on every new/`/clear` session, in exchange for the token savings.

**Out of scope for this decision:** semantic filtering beyond domain (e.g. a textual `search` using something from the user's prompt — there is no prompt yet at this point in the hook's lifecycle), configuring the 15-entry limit or the 5s timeout via env var (hardcoded in this first version, the same minimalist spirit as [D14](D14-claude-code-hook-auto-capture.md)), and applying the same mechanism to `pi` (no native hook, the same exception already recorded in [D14](D14-claude-code-hook-auto-capture.md) item 1).

**Elaboration — filtering non-extracted entries (found in production, still 16 Jul 2026):** the end-to-end manual test against the real `m3m0s serve` showed `additionalContext` injecting, as result #1, an entire raw-content fallback ([D12](D12-llm-fact-extraction.md) item 5 — extraction timed out on a `PreCompact` digest and the pipeline fell to the documented fallback) — literally the same kind of entry that motivated the retroactive extraction job ([D16](D16-in-process-jobs.md)). The maintainer flagged the problem: injecting that is bad in two ways — (1) it is an uncurated dump competing for space with real atomic facts, and (2) in the specific case of `PreCompact`, it may be **redundant** with the summary Claude Code itself just generated in the compaction that triggered that digest. Fixed with `injectableEntries` (`internal/hook/sessionstart.go`): it filters by the presence of `metadata.source_content` (`apitypes.MetadataKeySourceContent`, new — the same literal value `"source_content"` as the unexported constant already used in `internal/store/store.go`, without creating an apitypes→store dependency) before building the `ContextBlock`. Since non-extracted entries tend to pile up right at the top of `/recent` (they are the most recent by definition), the initial fetch went up from 15 to `sessionStartFetchLimit = 40` — the filter happens afterwards, in memory, and the final result is still cut to 15 (`sessionStartRecentLimit`) — preventing a streak of consecutive timeouts from emptying the injected digest for lack of margin. Entries excluded here are not lost nor treated as an error: they keep existing normally and are picked up by retroactive extraction ([D16](D16-in-process-jobs.md)) on the next run of the job — this filter only avoids injecting them **before** they are curated.
