# D36 — Runtime embedding configuration and vector spaces

**Status:** Accepted (issue #39; phase 1: configuration and per-row provenance; phase 2: the re-embedding job, below; phase 3: the WebUI page and CLI, below)

**Context:** the embedding model was a literal in the code, and only the endpoint and key could be set, by environment variable at boot. An admin could not change the model, ask for fewer dimensions (to shrink the in-memory index, #37) or rotate the provider without a redeploy. Vectors from different models or dimensions are not comparable, so a change has to be handled explicitly.

**Decision:**
- **Where it lives.** One row in the `embedding_config` table (enabled, base URL, API key, model, requested `dimensions`, and the vector length the provider returned when it was saved). With no row the environment still bootstraps the server exactly as before (`OPENAI_API_KEY`, `M3M0S_OPENAI_BASE_URL`, `text-embedding-3-small`, provider-default size). Once an admin saves a configuration the row wins; an empty saved key falls back to the environment key.
- **Vector space = (model, dimensions).** Each stored embedding records `embedding_model` and `embedding_dims`. Rows written before the migration have NULL there and are read as `text-embedding-3-small` with `length(embedding)/4` dimensions; the migration does not backfill, because an UPDATE would rewrite every ~6 KB blob (hundreds of MB of WAL on a small disk) to store what is already implied.
- **Only the active space is searched.** At boot (and after every change) the int8 index is rebuilt from the rows of the active space and takes its dimension from the configuration, not from the first vector it sees. Dedup and vector search therefore never compare across spaces. Rows from another space are still found by FTS5 (hybrid search, D32) until they are re-embedded. A keyword-only server (no key, or disabled) does not load the index at all.
- **Validation before saving.** `PUT /embedding-config` makes a real embeddings call with the proposed settings; it is rejected (422) when the call fails or the provider returns a different size than the requested `dimensions`. A rejected change leaves the active configuration untouched.
- **Confirmation.** If the change leaves stored vectors from another space (`stale > 0`), the request needs `confirm_reembed: true`, otherwise it answers 409 with the count. The cost estimate to show before confirming is `POST /embedding-config/reembed/estimate` (phase 2).
- **Secrets.** The API key is write-only: no response carries it, only `has_api_key` and `key_source`. It is stored as plain text in the same SQLite file that holds every memory, so it has the same exposure as the data it protects, so keep the data directory private; encrypting it with a key kept in the same directory would add no real protection. Environment variables remain the way to keep it out of the database.
- **Authorization.** Any authenticated caller (API key or account session) can read and change it: today every account is an admin of the single memory (D35). If roles are added, this endpoint becomes admin-only.
- **In-flight writes.** A write that embedded with the previous configuration and finishes after a switch is stored without its vector when the size differs (the re-embedding job fills it in). A same-size vector from a different model in that millisecond window would be mis-tagged; accepted as negligible for a single-admin system.

**Consequences:** the model name shown in `GET /stats` and the startup log is the configured one. Phase 3 the WebUI settings page and `m3m0s embedding show|set`, and phase 4 uses `dimensions` to shrink the index, validated with `m3m0s eval`.

## Phase 2: the re-embedding job

- **Job, not a new mechanism.** `embedding-reembed` is registered in the existing scheduler (D27) and shows on the Jobs page with `done/total/errors/ETA`. It is *manual* (interval 0): it spends provider tokens, so it never runs on a timer. It starts from `POST /embedding-config/reembed`, or from a `PUT /embedding-config` with `confirm_reembed: true` that leaves stale vectors (`reembed_started` in the response). The scheduler gained manual jobs, `Cancel(name)` and an optional `Progress` hook for this.
- **State is the database.** Pending = every row not in the active space: another model/dimensions, legacy NULL rows read through `COALESCE` (D36 phase 1), and rows with no vector at all (stored while keyword-only, or whose vector was dropped). There is no state table: cancelling, a crash or a restart loses nothing, and starting again continues with what is still pending. The job is not auto-resumed at boot, because that would spend money without a fresh confirmation; the admin presses start again.
- **Mechanics.** Keyset pagination by id (a row that keeps failing is skipped for this run and stays pending for the next). Batches of 64 texts (`M3M0S_REEMBED_BATCH`, max 2048) capped at ~200k characters per request, at most 5 requests/s (`M3M0S_REEMBED_RPS`). Transient errors (network, 408, 429, 5xx) retry up to 6 times with exponential backoff (1s doubling to 30s); then the run stops with the error. 401/403/404 stop it at once (they would fail for every row). Any other failure of a multi-text request is retried text by text, so one bad entry costs one error, not the batch. Text is truncated as in `Add`.
- **The race documented above, closed for the job.** The embedder (an immutable value that `SetEmbeddingSettings` replaces under the write lock) is captured before the provider call. The result is stored only while that same embedder is still active, checked and written under one read lock; otherwise it is discarded and the pending set is recomputed for the new space (progress restarts from 0 of the new total). The `UPDATE` also requires that the row still has the content that was embedded and is still outside the space, so an edit or a concurrent write is never overwritten by an older vector. The in-memory int8 index is updated as each row is stored, so search uses re-embedded rows right away; the rest are found by FTS5 meanwhile (D32).
- **Estimate.** `POST /embedding-config/reembed/estimate` (read-only; optional `model`/`base_url`/`dimensions` describe a change not yet applied) returns the pending rows, characters and `estimated_tokens` = characters / 4, which is an approximation. `estimated_cost_usd` is filled only for models with a known OpenAI list price (`text-embedding-3-small` 0.02, `-3-large` 0.13, `ada-002` 0.10 USD per 1M tokens, a dated constant in `internal/store/reembed.go`) and only on the public OpenAI endpoint; otherwise it is `null`. Prices are never guessed.
- **Not in this phase.** Using `dimensions` to shrink the index and measuring recall (phase 4).

## Phase 3: WebUI page and CLI

- **No backend change.** Both surfaces use the existing routes. The 409 flow is the same in each: on `reembed_required` they call `POST .../reembed/estimate` with the proposed model/endpoint/dimensions, show the pending rows, approximate tokens (characters / 4) and the cost (only when the server knows a list price, otherwise "unknown"), and resend with `confirm_reembed: true` only after an explicit confirmation.
- **WebUI.** An "Embedding" page (`/embedding`) with the configuration form and a re-embedding panel (start with a cost confirmation, cancel, progress bar with done/total, errors and ETA, polled every 2s only while a run is active, "up to date" state). The key field is write-only and empty on load; empty means keep, a checkbox removes a saved key. 422 messages from the provider are shown inline.
- **CLI.** `m3m0s embedding show|set|estimate|reembed start|status|cancel [--watch]`. `set` reads the current configuration and merges the given flags over it. The key comes from `--api-key-stdin` or `--api-key-env VAR` only, so it never reaches shell history or `ps`; output never contains it. Without a terminal, a 409 needs `--confirm-reembed`/`--yes`.
