# D35 — Accounts: onboarding, sessions and CLI-issued password reset

**Status:** Accepted (issue #35)

**Context:** the WebUI signed in by pasting an API key into the browser's local storage: no account, no revocable session, no first-run setup and no recovery path other than handling keys by hand.

**Decision:**
- **Accounts are for people; API keys stay for machines.** Hooks, MCP, the CLI and scripts keep `Authorization: Bearer <key>`. Accounts add username/password sign-in for the WebUI. All accounts share the one memory (an account is a login, not a separate memory), consistent with "one memory per person".
- **Onboarding needs an API key.** While no account exists the WebUI offers a first-run page, but `POST /auth/onboard` requires a valid API key (the one printed at first boot, or any existing one). The API is reachable before any account exists, so without that proof the first stranger to reach a fresh instance could claim it. It is refused once any account exists (a single guarded `INSERT`, so two simultaneous onboardings cannot both win).
- **Passwords:** salted PBKDF2-HMAC-SHA256, 600,000 iterations, from the standard library. It adds no dependency and, unlike a memory-hard KDF, does not spike the memory of a small host on login (the production host runs under a memory limit). Policy is length only (10-128), not equal to the username. Login does the same work for an unknown user as for a wrong password and answers the same, so accounts cannot be enumerated.
- **Sessions:** a random 256-bit token in an HttpOnly, `SameSite=Lax` cookie (`Secure` behind an https proxy), stored server-side only as a SHA-256 hash, 30-day lifetime, revoked by logout or password change. Because the cookie is sent automatically, every state-changing request it authenticates must carry `X-M3m0s-Csrf`, which a cross-site form cannot set; CORS stays `*` without credentials, so other origins cannot use the cookie at all.
- **Throttling:** after 5 consecutive failures a username, and separately an address (the last `X-Forwarded-For` entry, i.e. the one the reverse proxy appended), is locked for a doubling delay up to 15 minutes. Unknown usernames count too. The table is bounded and in memory (a restart clears it).
- **Reset is issued from the CLI, completed in the browser.** `m3m0s user reset <name>` (API key, never a browser session) prints a link with a random single-use token valid for 30 minutes. The page behind it checks the link, asks for the new password twice, and completing it consumes the link and revokes every session of the account. Only the newest link of an account works, a password that fails validation does not burn the link, and the current password keeps working until the reset completes (so issuing a link cannot lock the owner out). The same mechanism invites further accounts: `m3m0s user add` creates an account with no password and prints a longer-lived (72 h) link.
- **The CLI works over the API**, so it runs from any machine that has the API key. That makes the API key the root of trust: whoever holds it can already read and write all memory, and can now also reset an account. A password forgotten with no API key left means regaining a key from the server's data directory/host, which is the operator's recovery path.

**Not done:** changing a password while signed in, listing/revoking individual sessions, two-factor authentication, and roles (all accounts are equal). A reverse proxy that already authenticates the WebUI (for example a forward-auth login in front of `/`) still works and simply adds a second login.
