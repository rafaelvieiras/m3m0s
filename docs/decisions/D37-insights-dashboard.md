# D37 — Memory health dashboard: live overview and a read-only hygiene job

**Status:** Accepted

**Context:** a survey of a production-sized snapshot (77k memories, 8 Oct 2026) showed what a long-lived collection collects: near-duplicates that the add-time dedup cannot catch (it only compares inside one domain, and only against the top candidate), fragments of the extractor's own prompt and of `/compact` boilerplate stored as facts, 97% of memories never read, and most `valid_until` already past. None of this was visible without ad-hoc scripts. The goal is a page that shows it, without adding cost to the server: production is a small host with a ~600 MiB limit and the process already holds ~210-340 MB.

**Decision:**
- **Two tiers.** *Cheap* metrics (totals, distributions by domain, tool, age and text length, soft-deleted per day, `valid_until`/pinned/never-accessed, extracted versus raw) and the *forgetting outlook* are computed on request by one pass over the in-memory index, which already holds every entry without its embedding (~100 ms for 77k memories, no new allocations of note, no cache needed). *Expensive* analyses (identical text, near-duplicates, noise patterns) are a **job**, `insights-hygiene`, registered as manual in the existing scheduler like `embedding-reembed` (D36): progress and cancel on the Jobs page, an interval can be set later. Its last result is one JSON document in a new table `insight_reports` (migration 00006, one row per report name, replaced on every run); the dashboard reads it and shows when it was computed. A cancelled or failed run keeps the previous report.
- **Read-only.** The job never writes to `entries` or to the in-memory index; the only write is the report row. There is no "apply" step here: acting on the candidates stays with `forget-sweep`/`restore` (D22) and a future explicit, confirmed workflow. Tests assert that the entries table, the embeddings and the index are identical before and after a run.
- **Forgetting.** `ForgettingStats` classifies entries with the same eligibility rule and `retentionScore` as `sweepCandidates` (D22) but only counts, instead of building id lists; a test pins its numbers to `ForgetSweep(dryRun=true)`. It reports cold-now, soft-deleted waiting for the hard-delete, those already past the grace window, the exempt (raw or pinned), and a retention-score histogram.
- **Near-duplicates without a matrix.** No float32 vectors are loaded and no NxN matrix is built. Candidates come from the int8 index (D31): up to 3000 vectors are compared all-pairs; beyond that, random-hyperplane hashing (24 tables of 14 bits, vectors centered on their mean, buckets capped at a 256-wide window) generates candidate pairs, and each candidate is verified with the same int8 dot product search uses. Per table it keeps only 2 bytes per row; found pairs are capped (300k). Reads of the index are in slices under its read lock (never held across a whole pass), rows are re-checked against the id snapshot so concurrent inserts or removals are safe, and the PRNG is seeded so the same data gives the same result. Exact brute force over 76k vectors would be about 3 billion dot products; hashing makes it a ~15 s job. The price is recall: against exact float32 cosine on a 76k-memory snapshot (512 dimensions), it found 99.1% of pairs at >= 0.98, 99.7% at >= 0.95 and 96.4% at >= 0.92, so counts are a slight lower bound (documented in the API contract).
- **Limits on the job.** A duty cycle (`M3M0S_INSIGHTS_CPU_PERCENT`, default 60: it sleeps after each slice of work), a wall-clock limit (`M3M0S_INSIGHTS_MAX_MINUTES`, default 30, after which it stores a partial report flagged `partial`), cancellation checked between slices, and a tighter GC target while it runs (the heap goal is a multiple of the large index, so default pacing let small allocations pile up to tens of MB), followed by returning memory to the OS. It needs no network.
- **Noise patterns.** For the `codigo` category only. *Conservative* (A: the extractor's prompt leaking into facts; B: `/compact` and session-continuation boilerplate; C: a commit-message generator's fixed prompt) are narrow regexes, with A limited to extracted entries and excluding synced docs. *For review* (D: diff trivia such as byte sizes; E: "The text describes ..." meta-descriptions; F: short with no identifier) are reported but never suggested for automatic action, because the survey measured real false positives. Per criterion: matches, never-accessed matches, and examples.
- **Security.** Same authentication as the other admin endpoints. No embedding leaves the server. Examples are truncated to ~160 characters, e-mail addresses and phone numbers are masked, and a memory that matches any secret pattern of the ingestion redactor (`internal/redact`) is omitted from every example list (still counted).
- **Surfaces.** `GET /insights/overview`, `GET /insights/hygiene`, `POST /insights/hygiene/run|cancel` (types in `internal/apitypes`), the WebUI "Insights" page (CSS bars, no chart library; expandable examples; a "Run analysis" button with progress and last-run date; an explicit empty state), and `m3m0s insights show [--json]`.

**Measured (8 Oct 2026, copy of the production snapshot, 76k active memories, 512 dimensions, local server with no network):** job 15 s at 100% duty and 28 s at the default 60%; process RSS +21 MB at the peak over an idle 144 MB (the boot `VmHWM` of ~177 MB is not exceeded) and back to 144 MB afterwards; the overview answers in ~100-130 ms. With 1536-dimension vectors (same entries) the job took 72 s at the default duty cycle, RSS +24 MB at the peak over an idle 223 MB, and 219 MB after.

**Not in this decision:** acting on candidates (soft-delete/merge from the page), conflict detection (the survey found a heuristic for it too imprecise), scheduling by default, and prevention at ingestion (filters for the A/B/C patterns in `add`).
