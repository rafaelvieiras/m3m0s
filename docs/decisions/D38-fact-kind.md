# D38 — Fact nature (`kind`): closed enum, extractor tag, heuristic fallback, stored in metadata

**Status:** Accepted

**Context:** the forgetting job (D22) applies one retention formula, based on age and access, to every extracted fact. On a production-sized collection (about 78k memories, 83 days old, 96.6% never read) that formula cannot tell a durable fact (a decision, a root cause, a convention) from a transient one (task status, a diff statistic, a one-off command): in a hand-judged sample of 80 facts, half of those the current cut would delete within 30 days were durable. A better retention policy needs a signal about the nature of a fact first. This decision adds the signal (issue #51); the per-kind retention policy is a separate step that builds on it. Depends on D12 (extraction), touches D22 (it only adds the signal, retention is unchanged).

**Decision:**
- **Closed enum.** `decision` (a choice and, ideally, why), `rule` (convention, constraint, standing instruction), `preference` (a stated preference of the user), `gotcha` (root cause, pitfall, non-obvious behaviour), `procedure` (how to do something), `state` (a transient status), `noise` (meta-description, boilerplate, diff trivia), `other` (default when unsure). `decision`, `rule`, `preference`, `gotcha`, `procedure` are *durable*, `state` and `noise` *transient*, `other` neither (`factkind.Durable/Transient`; the agreement report uses this split). Adding a value is a constant plus an entry in `factkind.All`; nothing is persisted as an enum, so old data is never invalid.
- **Extractor (D12).** The prompt asks for `{"facts":[{"text","kind"}]}` in the same call: no extra LLM request, a few tokens more per fact. Parsing accepts the old bare-string facts too (a provider that ignores the schema): those have no kind and get the heuristic. An unknown kind value (any casing or padding is normalized first) becomes `other`. `extract.Extractor.ExtractFacts` returns the kinds; `Extract` keeps returning plain strings; `store` sees them through an optional `KindExtractor` interface (like `Classifier` in D15), so fakes and older providers keep working. The prompt is pinned by `internal/extract/testdata/system_prompt.golden.txt` and the parsing by `testdata/golden_extraction.json`.
- **Storage: metadata keys, no migration.** `metadata.kind` and `metadata.kind_source` (`llm` | `heuristic` | `manual`), reserved like `pinned` or `valid_until`. The alternative was a nullable column from migration `00007`. Metadata wins here because: (1) it is the established home of per-fact signals the retention code already reads (`pinned`, `access_count`, `deleted_at`, `valid_until`) and the whole map is already in the in-memory index, so filters, the Insights distribution and the future retention pass cost no query and need no new index; (2) no schema change means nothing to migrate, roll back or keep in step across the SQLite and in-memory representations, and existing rows are provably untouched (a test opens a store over legacy rows and checks that neither `metadata` nor `updated_at` changed); (3) `UpdateMetadata` can write a tag without re-embedding or touching `updated_at`, which a backfill needs. The price is that it is not queryable in SQL; nothing queries it in SQL, and the column can still be introduced later by a migration that copies the key. A missing or invalid value **reads as `other`** (`Entry.KindValue`), and `kind_source` is simply absent for such rows. The public JSON adds derived top-level `kind` and `kindSource` fields (`Entry.MarshalJSON`); the stored form stays in `metadata`.
- **Heuristic fallback** (`factkind.Classify`) for servers without an extractor and for every raw-fallback path (extraction failed, or disabled), tagged `kind_source=heuristic`. It is deliberately conservative: families of marker patterns (noise: `N files changed`, `N insertions(+)`, "The text describes..."; state: `Status:`, "is currently waiting", "N of M tasks done"; gotcha: "root cause", "caused by", "turns out", "workaround"; decision: "decided to", "opted for", "switched to"; rule: "always/never <verb>", "must be", "convention:"; preference: "the user prefers", "I prefer"; procedure: "to deploy ... run", "steps:", "how to") and a kind is returned only when **exactly one family matches** in the first 2000 characters; two families, or none, mean `other`. Silence is the common outcome by design: the prototype described in #51 got 27/29 right when it decided but left 46% of the "neutral" bucket actually transient, so it is a stopgap, not a replacement for the LLM tag. It is not a retention input on its own.
- **Never overwriting a human.** `memory_update` takes `kind` (validated against the enum, `400 invalid_kind`) and sets `kind_source=manual`. A `manual` tag is kept by: dedup merges (`adoptKind`: the merged entry keeps its tag; an LLM tag replaces a heuristic or missing one only), `metadata` replacement (it cannot set or drop the reserved keys; a machine tag is dropped, a manual one is kept), retroactive re-extraction (kept when the entry yields a single fact), and the backfill. `pinned` keeps its meaning (exempt from decay) and is independent of `kind`.
- **Existing entries: optional backfill, no UPDATE in a migration.** Job `kind-backfill` (manual, like `embedding-reembed` in D36). It does **not** re-extract: facts that already went through extraction are atomic, so re-running the retroactive-extraction path (delete + reinsert, new ids, broken `related_to`) would be costly and destructive; instead the extractor gets a classification-only call (`ClassifyKinds`, 20 facts per request by default, each cut to 600 characters, JSON answer with exactly one kind per fact). Raw entries still go through the normal retroactive extraction (D12), which now tags the facts it produces. Pending = active entries with no tag; heuristic tags too while an LLM classifier is available (it improves them); `manual` and `llm` never. The state is the data, so a stopped, crashed or cancelled run resumes by starting again (an LLM tag is final, a failed batch stays pending). Rate limited (`M3M0S_KIND_BACKFILL_RPS`, default 1 request/s; `M3M0S_KIND_BACKFILL_BATCH`), it gives up after 5 consecutive failed batches, and each write re-checks under the lock that the entry still exists with the classified content and no manual/LLM tag (a concurrent edit is counted as skipped), writing only `metadata_json` and keeping `updated_at`. **Cost is estimated first** (`POST /kinds/backfill/estimate`: facts, requests, tokens at characters / 4, cost only when the operator gave the model's prices in `M3M0S_EXTRACT_PRICE_IN_PER_MTOK` / `..._OUT_...`, because the project keeps no price table for arbitrary chat models) and **starting needs explicit confirmation** (`{"confirm": true}`, `--yes` in the CLI, a prompt otherwise); triggering the job from the Jobs page without it returns an error instead of spending tokens. Without an extractor the job runs the free heuristic and needs no confirmation.
- **Exposure.** `kind`/`kindSource` in the memory JSON (`docs/api-contract.md`), `kind` filter on `memory_search` and `memory_recent` (API, MCP, CLI `--kind`; `other` also matches untagged entries), `kind` in `memory_update`/`m3m0s update --kind`, the distribution (`by_kind`, `by_kind_source`) in `GET /insights/overview`, `m3m0s insights show` and the Insights page, and a kind badge on the entry page.
- **Measuring it.** `GET /kinds/sample` / `m3m0s kind sample --n 200 [--blind]` exports facts spread over domain categories and age buckets (round robin over the strata, seeded, content redacted and cut); `--blind` keeps the server's tags in a separate file so they do not anchor the labeller. A person fills `label`; `m3m0s kind report --file sample.json [--predictions ...] [--stored-source llm]` prints, offline, exact agreement and per-class precision/recall for the stored tag and for the heuristic re-run on the content, plus **durable-vs-transient agreement** (computed where both the label and the prediction took a side, with the coverage of that comparison). The target of #51 is durable-vs-transient agreement >= 85%. The golden file (`TestGoldenLive`, opt-in with `M3M0S_GOLDEN_LIVE=1`) runs the golden inputs against a real model to compare a prompt or model change.

**Limits and not in this decision:** the hand-labelled sample of >= 200 facts and the agreement figures from it are still to be produced (the tooling is here; the numbers are not); the heuristic is English-centred plus structure markers, so other languages mostly get `other`; classification sees only the first 600 characters of a fact in the backfill; a metadata replacement drops a machine tag until the next backfill; there is no automatic backfill schedule and no retention behaviour per kind (D22's formula is unchanged: that is the next step, which can now read `Entry.KindValue()`); the kind of an entry is not re-derived when its content is edited (only a human or the backfill changes it).
