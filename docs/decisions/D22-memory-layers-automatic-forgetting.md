# D22 — Memory layers / automatic forgetting, inspired by ai-memory (closes A9)

**Status:** Accepted. The retention score below (single 30-day half-life) is revised by [D39](D39-per-kind-retention.md), a half-life by kind that is opt-in (`M3M0S_RETENTION_MODEL=per-kind`); this formula remains the default.

**Context:** the maintainer asked, on 17 Jul 2026, to implement "memory layers" following the model of `akitaonrails/ai-memory` (analyzed on the same day in a comparative benchmark) — which has 4 explicit tiers (working/episodic/semantic/procedural) with a decay formula (`salience · exp(−λΔt) + σ · log(1+access_count) · exp(−μ · days_since_access)`) and a scheduled `forget-sweep` (soft-delete → hard-delete after a window). This is exactly what [A9](A9-old-memory-compression.md) had left open since the foundation ("compression of old low-value memories") without ever becoming a decision — the same caution as [A7](A7-source-content-duplication.md)/[D21](D21-deduplicated-source-blob-store.md) (it touches mass deletion), so before coding, the 2 questions that [A9](A9-old-memory-compression.md) already recorded as blockers were closed with the maintainer via structured questions:

1. **Destructive or not:** soft-delete + hard-delete after a grace period (recommended and chosen) — not "report only" (it would not implement anything by itself) nor "soft-delete only forever" (it never really frees space). Reversible within the window via `Restore`.
2. **Decay scope:** only facts that went through fact extraction (Phase 4/[D12](D12-llm-fact-extraction.md) — they have `metadata.source_content_ref`) decay by default (recommended and chosen); raw manual content or content that fell to the extraction fallback ([D12](D12-llm-fact-extraction.md), item 5) is treated as more deliberate and is exempt.

**Adaptation to m3m0s's model:** m3m0s does not have ai-memory's concept of a per-session compiled "page" ([D12](D12-llm-fact-extraction.md) already decided 1 fact = 1 atomic `Entry`, not 1 rewritten page) — so, instead of porting their 4 explicit tiers, a single retention formula (`internal/store/decay.go`) decides eligibility and coldness:

- `retentionScore(e, now) = exp(−ln2·age/30d) + 0.5 · log1p(access_count) · exp(−ln2·days_since_last_access/45d)` — the first term is pure age decay (a 30-day half-life, the same order of magnitude as ai-memory's "30d hot"); the second is access reinforcement (one more recent access "holds" a live memory longer than age alone would allow). `log1p`, not raw `access_count`, for diminishing returns. Below `ColdRetentionThreshold = 0.15`, it becomes a soft-delete candidate.
- **Eligibility** (`isDecayEligible`): `metadata.source_content_ref` present (an extracted fact, [D12](D12-llm-fact-extraction.md)) AND `metadata.pinned` != `"true"` — the latter is an explicit exemption mechanism à la ai-memory's "pinned: true", editable today even without a dedicated UI (any `PATCH /memories/:id` that touches `metadata` already accepts the key).
- **Reinforcement** (`touchAccess`, `metadata.access_count`/`last_accessed_at`): every `Get` and every PRIMARY `Search` hit (not those brought in by the 1-hop expansion of `related_to`, Phase 7/[D15](D15-light-kg-temporal-fact.md) — they were not deliberately found by that query) bumps the counter. `Recent` does not reinforce (listing is not "finding"). It rewrites only the metadata in chromem-go reusing the already-computed embedding (the same technique as `migrateOneSourceContentBlob`, [D21](D21-deduplicated-source-blob-store.md)) — it never spends a new embedding call per read.
- **`ForgetSweep(dryRun, now)`:** scans the index, classifies each eligible entry by score, soft-deletes (`metadata.deleted_at`) the cold ones (`dryRun=false`) and hard-deletes (the same `Delete` as the cascading purge of Phase 2) the ones that have been soft-deleted for more than `SoftDeleteGraceDays = 30` days. `dryRun=true` only reports candidates (`SoftDeleteCandidates`/`HardDeleteCandidates`), changes nothing — meant for manual preview before trusting the scheduled job.
- **`Restore(id, now)`:** reverts a soft-delete at any time before the corresponding hard-delete — the same `ErrNotFound` both for "id never existed" and "id exists but is not soft-deleted", on purpose (the caller only needs to know "nothing to restore here").
- **Soft-deleted is invisible by default:** `Get` returns `ErrNotFound` (the same public semantics as "does not exist"), `Search`/`Recent`/`expandRelated` skip it, and `findDuplicate` treats a soft-deleted candidate as "no duplicate" — without this, an `Add` of repeated content would silently revive a memory the sweep had decided to forget, behind the back of `Restore`.

**New surfaces** (the same pattern as the 3 layers — HTTP/MCP/CLI): `POST /api/v1/memories/forget-sweep` (optional body `{"dryRun": bool}`), `POST /api/v1/memories/:id/restore`, MCP tools `memory_forget_sweep`/`memory_restore`, CLI `m3m0s forget-sweep [--dry-run]`/`m3m0s restore <id>`. `GET /api/v1/stats` gains `telemetry.softDeletedCount`.

**Scheduled job:** `internal/jobs` ([D16](D16-in-process-jobs.md)) gains `forget-sweep`, registered **always** (not only when fact extraction is enabled — unlike `retroactive-extraction`, eligibility does not depend on there being an `Extractor` configured IN THIS run, only on the entry already having `source_content_ref` from some earlier boot). Interval configurable via `-forget-sweep-interval`/`M3M0S_FORGET_SWEEP_INTERVAL` (default 12h), `InitialDelay` of 5 minutes.

**Out of scope:** ai-memory's 4 explicit tiers (working/episodic/semantic/procedural) were not ported — they do not map cleanly onto m3m0s's flat `Entry` model, and a single formula with a `pinned` exemption field covers the same practical goal without the complexity of 4 parallel categories. Fine-tuning the constants (`DecayAgeHalfLifeDays`, `ColdRetentionThreshold`, etc.) is left for when there is real production data showing that the defaults chosen here are off by a lot in either direction — they are not critical infra, just starting values documented in `internal/store/decay.go` itself.
