# D28 — Replace the hand-rolled JSONs + chromem-go with SQLite and versioned migrations

**Status:** Accepted

**Context:** the maintainer noticed that every m3m0s schema evolution so far was done by hand, with no migration mechanism at all, and asked for an analysis before any new implementation. A survey confirmed the problem: 6 JSON files persisted in `dataDir` (`index.json`, `sourceblobs.json` [D21](D21-deduplicated-source-blob-store.md), `telemetry.json`, `jobs-config.json` [D27](D27-webui-jobs-visibility-control.md), `apikeys.json`, `selfdocs-state.json` [D25](D25-embedded-docs-self-indexing.md)), each with hand-rolled load/save (atomic tmp+rename) and no version field whatsoever. Worse: each `Entry` lived in **two independent representations** — `index.json` (a direct dump of `schema.Entry`) and chromem-go's internal document (flattened via `Entry.ToMetadata()`/`FromMetadata()`, with the embedding) — any change to that mapping had to be migrated in both places in sync by hand; it only happened correctly once (`internal/store/migrate.go`, [D21](D21-deduplicated-source-blob-store.md)), in an entirely bespoke way. Asked about the scope via structured questions, the maintainer explicitly chose to **replace everything, including vector search**, reopening the part of [D2](D2-stack-go-core-typescript-only-where-required.md) that chose chromem-go as the vector layer (the rest of [D2](D2-stack-go-core-typescript-only-where-required.md) — Go core, static binary — does not change).

**Stack:** `modernc.org/sqlite` (a pure-Go driver, zero cgo — critical: the `Dockerfile` builds with `CGO_ENABLED=0` to keep the static binary that [D2](D2-stack-go-core-typescript-only-where-required.md)/[D4](D4-host-docker-on-desktop-first.md) require for the Raspberry Pi) + `github.com/pressly/goose/v3` as the migrations runner (versioned SQL, embedded via `go:embed` — the same pattern already used for `webui/dist` and `selfdocs`). A homegrown runner was considered and discarded: it would reimplement checksum/ordering/"dirty" state that goose already solves in a tested way, with no real gain in a layer as critical as the one that holds all of the product's data.

**Vector search without a native extension:** chromem-go already did exact brute-force search (no ANN index), suited to m3m0s's personal volume. Switching to SQLite loses no search quality at all: the embedding sits in a `BLOB` column (little-endian float32) of the `entries` table; `internal/store/similarity.go` computes cosine in Go over the set already filtered by domain (`scoreDomainCandidates`, replacing the `where` that went to chromem-go's `collection.Query`). `sqlite-vec` (a native vector extension) was discarded on purpose — it normally requires cgo, which would break the static binary.

**Schema (`internal/sqlstore/migrations/00001_init.sql`):** `entries` (id, content, domain, domain_category, source, agent, tags_json, metadata_json, created_at, updated_at, embedding) — `metadata_json` remains the **complete and identical** round-trip of `schema.Entry.Metadata`, including the reserved keys that already lived there before ([D12](D12-llm-fact-extraction.md)/[D15](D15-light-kg-temporal-fact.md)/[D21](D21-deduplicated-source-blob-store.md)/[D22](D22-memory-layers-automatic-forgetting.md): `source_content_ref`/`related_to`/`valid_until`/`pinned`/`access_count`/`last_accessed_at`) — D28 did not promote those keys to columns of their own (unlike what the original plan considered): the in-memory index (`MemoryStore.index`, see the next section) already solves filtering in Go without needing a `WHERE` on those columns, and adding that extra layer would only increase the migration risk with no real need at m3m0s's personal scale. `source_blobs` ([D21](D21-deduplicated-source-blob-store.md)), `api_keys`, `job_intervals` ([D27](D27-webui-jobs-visibility-control.md)), `telemetry` complete the schema — each replacing 1 of the old JSONs.

**`internal/store` keeps an in-memory index** (`map[string]schema.Entry`, the same role as before D28: a fast source of truth for `/recent`/`/stats`, reloaded from SQLite at boot) — it did not become a SQL-first redesign of every method. Every write that previously did "chromem AddDocument + rewrite the entire `index.json`" now does **1 single row upsert** (`sqlstore.UpsertEntry`) — and as a bonus, a performance improvement (writes stop being O(total index size) and become O(1)). Operations that only change metadata without touching the embedding (access reinforcement [D22](D22-memory-layers-automatic-forgetting.md), soft-delete, `Restore`, `linkRelated`) use `UpdateMetadata` — a partial `UPDATE` that never touches the `embedding` column, simpler than the `GetByID`+`AddDocument` that `rewriteChromemMetadata` had to do before just to preserve the already-computed vector.

**Legacy data import (`internal/store/importlegacy.go`):** runs only once (`ImportLegacyData`, called by `cmd/m3m0s/serve.go` right after `store.New`, before anything else touches the database) — a no-op if the `entries` table already has rows. It reads the 6 old JSONs, accepts both raw `source_content` and `source_content_ref` (covering whoever never ran [D21](D21-deduplicated-source-blob-store.md)), and fetches each entry's embedding from the legacy chromem-go (opened read-only, via `chromem.NewPersistentDB` pointing at the same `dataDir` — chromem-go remains in `go.mod`, used only by this import path, no longer by the serving path). Without a legacy embedding available (a partial install), it recomputes via `embedFunc` instead of discarding the entry — never silently losing data matters more than saving 1 API call in an import that runs only once. The old files are **not deleted automatically** — they stay as harmless dead weight until manual confirmation in production that SQLite is the source of truth.

**Removed:** `internal/store/migrate.go` ([D21](D21-deduplicated-source-blob-store.md)) — the equivalent effect (normalizing raw `source_content` into a blob) became part of the import above, instead of a scan on every boot. `chromem-go` stops being the serving vector layer (it only survives as a read dependency of the legacy import). `internal/embed` (a new package) ports the OpenAI-compatible embeddings HTTP call that chromem-go made internally — without its `normalized` flag, because the cosine similarity computed in `internal/store/similarity.go` already normalizes by the vectors' magnitudes, working correctly with or without prior normalization.

**Out of scope:** normalizing `tags`/`related_to` into tables of their own (kept as JSON/CSV inside `metadata_json`, the same format as before); any ANN index (brute force remains adequate at this scale); testing real cross-compilation for the Raspberry Pi (`modernc.org/sqlite` is pure Go, but testing on real ARM hardware is still waiting for Phase 6, [D4](D4-host-docker-on-desktop-first.md)).
