# D29 — Context-injection preview in the WebUI, before implementing new hooks/integrations

**Status:** Accepted

**Context (20 Jul 2026):** the maintainer wants to evaluate what the initial prompt injected into each tool they use (`pi`, Claude Code, OpenCode, scripts, cron) would look like BEFORE deciding to implement new hooks/integrations for them — a visual preview in the WebUI is needed, not yet another injection feature itself. Today only 1 automatic mechanism really exists: Claude Code's `SessionStart` hook ([D14](D14-claude-code-hook-auto-capture.md)/[D17](D17-sessionstart-memory-injection.md)). Asked via structured questions before coding, the maintainer closed the scope on 3 points: (1) a generic preview per **injection mechanism**, not per tool name — it avoids inventing mechanics that no tool has yet (e.g. an "automatic hook for `pi`" does not exist and should not appear as if it did); (2) reuse `apitypes.BuildContextBlock` as is, without opening the scope of redesigning the block's format; (3) feed the preview with a real domain, chosen in a text field — with no programmatic simulation of fictitious "empty database" scenarios (that case already shows up naturally when the typed domain has no memories).

**3 modes, the 3 mechanisms that really exist today (none invented):**
- `hook`: reproduces `internal/hook.RunSessionStart` ([D14](D14-claude-code-hook-auto-capture.md)/[D17](D17-sessionstart-memory-injection.md)) exactly — the same `SessionStartFetchLimit`/`SessionStartRecentLimit`/`InjectableEntries` (the 3 constants/function exported from `internal/hook`, D29 — they were unexported until now, only used inside the package itself), the same `hookSpecificOutput` JSON envelope.
- `mcp`: reproduces what the MCP tool `memory_recent` returns today (`internal/mcpserver`, `dispatchTool`) — with no extraction filter, in the same `content: [{type: "text", text: "..."}]` format as a tool result. It makes explicit that `pi`/OpenCode (generic MCP clients, with no hook of their own, [D10](D10-pi-adapter-dropped.md)) only see context if the model decides to call the tool — never automatically at the start of the session, unlike Claude Code.
- `manual`: raw `apitypes.BuildContextBlock`, with no envelope — the text one would paste by hand into the prompt of a tool with neither hook nor MCP (scripts, cron, a future agent not yet plugged in).

**Implementation:** `GET /api/v1/preview/injection?domain=X&mode=Y` (`internal/httpapi/preview.go`) runs inside `serve` itself, with direct access to `store.MemoryStore` (no HTTP round-trip to itself) — `mcpContentBlock`/`mcpToolResult`/`hookSessionStartOutput` are duplicated locally instead of imported from `internal/mcpserver`/`internal/hook` (they are the public contract of the MCP protocol and of the Claude Code hook, not an internal detail of the packages; importing `mcpserver` — client-side code — from inside `serve` would invert the dependency without need). Response: `{ mode, domain, mechanism, entriesFetched, entriesUsed, raw }` — `mechanism` is the description of the mechanism ready to display in the WebUI. Scope restricted to the WebUI (the same rationale as [D23](D23-webui-floating-llm-chat.md)) — no MCP tool nor CLI subcommand: it is an inspection tool, not a business operation that `pi`/scripts would need to call. A new `/preview` page (`webui/src/pages/PreviewPage.tsx`): a domain field (free text, the same pattern as `RecentPage`) + tabs (`Tabs`) for the 3 modes, both reflected in the route's search params (shareable URL). Validated end to end: Go tests hitting the real `Server.Handler()` (`internal/httpapi/preview_test.go`, the 3 modes + an invalid `mode` error) and, in addition, an isolated instance of `m3m0s serve` (local test data, never the production container) with a fake embed, actually opened in a browser via Playwright — the 3 modes and the empty state (a domain with no memories) rendering as expected.
