# D16 — In-process job system (periodic routines)

**Status:** Accepted

**Context:** found in production right after Phase 8 ([D14](D14-claude-code-hook-auto-capture.md)): the `m3m0s hook claude-code` hook sent a long session digest, fact extraction (Phase 4/[D12](D12-llm-fact-extraction.md)) hit a network timeout to the provider, and the pipeline fell back to the behavior documented in [D12](D12-llm-fact-extraction.md) item 5 (inserts the raw content, `Extracted: false`) — correct behavior (the memory is not lost), but it leaves that entry without ever going through extraction unless someone runs something extra. On the same day (16 Jul 2026) the maintainer asked for a generic routines/jobs mechanism for the server, with the first job addressing exactly this backlog: finding memories without extraction and running extraction on them retroactively.

**Decision, in 2 parts:**

1. **In-process scheduler, with no OS cron or external lib — `internal/jobs`.** A `Scheduler` with 1 goroutine and 1 short `time.Ticker` (meant for seconds — configurable via `-jobs-tick`/`M3M0S_JOBS_TICK`, default 30s) checks on every tick which registered `Job`s have passed their own `Interval` (meant for hours) and fires each one in its own goroutine — it never overlaps two runs of the same job (a run slower than `Interval` makes the next tick skip, not pile up). An error or panic inside a `Run` is only logged, never takes the process down. It reuses the same zero-dependency pattern as [D2](D2-stack-go-core-typescript-only-where-required.md) (Go in the core): no third-party cron lib, no systemd timer, no new infra — just `time.Ticker`.
2. **First job: retroactive extraction (`internal/store/retroextract.go`).** It scans the index for memories without `metadata.source_content` (the same signal that already distinguishes extracted from raw entries, [D13](D13-webui-admin-scope.md) item 3) — covering both entries inserted with extraction turned off and the timeout-fallback case above — and runs extraction on them, replacing each one with the N extracted facts (the same shape `Add` would have produced if extraction had run at the time). It is only registered when fact extraction is enabled (`M3M0S_EXTRACT_API_KEY` present — without it, it would be a perpetual no-op). Default interval 2h (`-retro-extract-interval`/`M3M0S_RETRO_EXTRACT_INTERVAL`), an `InitialDelay` of 2min after boot (it does not wait the whole interval to start clearing the existing backlog), a batch of up to 25 memories per run (`retroExtractionBatchLimit`, oldest first by `CreatedAt`) so it never locks the process in a single round — what is left becomes a candidate again on the next run.

**Job safeguards (found while writing the tests, not designed up front):**
- The original entry is only deleted **after** checking that its `UpdatedAt` still matches the snapshot read before the extraction network call — without that, a concurrent `memory_update` ([D13](D13-webui-admin-scope.md)) in the middle of extraction (which can take seconds) would be silently lost: the job would delete the ID holding the new content using facts extracted from the old content. If it changed (or was already deleted), the job skips that entry without error; it remains a candidate for the next round. This narrows the race window but does not eliminate it entirely (a smaller window still exists between the check and the delete) — accepted as a known limitation of this first version.
- The original entry is deleted **before** inserting the extracted facts (not after) — in the reverse order, the dedup/related pipeline ([D12](D12-llm-fact-extraction.md)/[D15](D15-light-kg-temporal-fact.md)) finds the original entry itself as a candidate (semantically similar by definition to the facts just generated from it) and either merges the fact back into it (silently losing the other facts), or links a `related_to` that is doomed to point at an ID the same method would delete right after. If inserting any fact fails after the delete, the original content is restored as a raw fallback (the same spirit as `Add`'s fallback when extraction fails, [D12](D12-llm-fact-extraction.md) item 5) — a memory is never lost because of a failure in the middle of the loop.

**Out of scope for this decision:** an HTTP endpoint to trigger the job manually, dedicated telemetry in `/stats` (how many memories are pending, when it last ran), and resolving pending `related_to` references that pointed at the deleted ID (they become orphaned — `expandRelated`, [D15](D15-light-kg-temporal-fact.md), already ignores an ID that no longer exists in the index, so this is harmless, it only loses that specific link). Any of these becomes a separate decision if the maintainer misses it in practice.
