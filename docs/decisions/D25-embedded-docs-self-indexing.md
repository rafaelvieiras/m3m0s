# D25 — Documentation embedded in the binary + self-indexing at boot (production, replaces D24 outside the dev desktop)

**Status:** Accepted

**Context:** the maintainer pointed out a real gap in [D24](D24-watch-on-own-repo.md) — the `m3m0s watch` that powers the project's self-documentation ran (and still runs) as a `systemd --user` process ON THE DEVELOPMENT HOST, reading `AGENTS.md`/`docs/*.md` directly from the cloned repo folder. That only works because the maintainer has the repo locally — it would not work in any real standalone Docker deployment (a Raspberry Pi, or anyone else who just pulls the image): the container has neither these `.md` files nor runs a `watch` inside. Asked via structured questions between 3 options (leave as is / run watch inside the container / embed in the binary + self-index at boot), the maintainer chose the 3rd, the one most aligned with the pattern already used for the WebUI ([D13](D13-webui-admin-scope.md)/[D15](D15-light-kg-temporal-fact.md) — `go:embed` + serving from the process itself, with no dependency on anything external).

**Two new packages:**
- **`selfdocs`** (repo root, not `internal/`): `//go:embed AGENTS.md docs/*.md docs/decisions/*.md` (originally `AGENTS.md docs/*.md`; extended when the decision records were split into `docs/decisions/`) — it has to be at the root because `go:embed` does not accept `..` in the pattern, and the files live at the repo root, not inside `internal/`. The import path becomes the module root itself, even though the package is named `selfdocs` — the only way to embed root files without moving them into a subdirectory. `CLAUDE.md` is left out (it is just a 1-line pointer to `AGENTS.md`, with no content of its own).
- **`internal/selfindex`**: orchestrates the indexing — it reuses `internal/chunker.Split` (the same header-based slicing as `m3m0s watch`, [D11](D11-watch-mechanism.md)) and calls `store.MemoryStore.Add`/`DeleteByFilePath` DIRECTLY, with no HTTP round-trip (unlike `internal/watch`, which by [D3](D3-decentralized-execution-core-vs-watch.md) is always an external HTTP client — here it is an internal bootstrap of `m3m0s serve` itself, it makes no sense to go out and back over the network to itself).

**Reserved domain/source:** `codigo:m3m0s` (the same domain already used by `m3m0s watch` on the host, [D24](D24-watch-on-own-repo.md) — on purpose, so as not to duplicate content under different domains if both mechanisms run at the same time), source `"selfdocs"` (it distinguishes provenance: "this came from the documentation embedded in the binary", different from `"watch"`/`"webui-chat"`/`"claude-code"`).

**Idempotence across restarts:** a sha256 hash per file, persisted in `<M3M0S_DATA_DIR>/selfdocs-state.json` (atomic tmp+rename, the same pattern as `internal/watch/state.go`/`internal/store`/`internal/auth`) — a hash equal to the already-indexed one is skipped without calling `Add` again (without that, every `docker restart` would reprocess everything and needlessly spend extraction tokens again). If the hash changed (docs edited in a rebuild) or it is the first time: it purges the old chunks of that `file_path` (cascade) and reindexes from scratch.

**Per-chunk/file failure isolation (the same rationale as [D24](D24-watch-on-own-repo.md), one layer down):** a chunk that fails (embedding down, timeout) is logged and skipped — it does not take down the rest of the file nor the other files. A file with 1+ failed chunks does not get its hash advanced, so the next run retries only what was left pending.

**Does not block boot:** fired in a separate goroutine right after the store is ready — the 1st indexing may legitimately take minutes (the same order of magnitude observed in [D24](D24-watch-on-own-repo.md)), and `/health` already answers while it runs in the background.

**Coexists with [D24](D24-watch-on-own-repo.md) without conflict:** if the maintainer keeps the host's `m3m0s-watch` on, the two mechanisms contend for the same domain/file_path consistently (they do not duplicate under different identities) — but they are redundant to each other. With the embedded self-indexing covering real production, the host's `systemd --user` becomes just a convenience for faster feedback during active doc editing (fsnotify reacts immediately; the embedded version only reindexes on the next boot/redeploy) — it can be turned off with no loss of functional coverage.

**Out of scope:** a flag to turn off self-indexing (it stays always on by default — it is the product's own knowledge, not user data, it makes sense in any deployment that runs this binary); GC of `selfdocs-state.json` if a file is removed from the embedded list (there is no real case of that today — the list is fixed in the source code).
