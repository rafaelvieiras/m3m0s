# D21 — Deduplicated blob store for `metadata.source_content` (closes A7)

**Status:** Accepted

**Context:** the maintainer reported the database size growing fast — 7MB with few conversations, a projection of 700MB in 100 days at the observed rate. Measured directly in production (16 Jul 2026, 220 entries): `metadata.source_content` is ~71x larger, in total, than the `content` of the facts themselves, and because of this: in a sample of 58 recent entries there were only 9 distinct source-text blocks, but some were shared (copied in full) by up to 14 different entries. This is exactly the design flagged as a risk in [A7](A7-source-content-duplication.md) — each extracted fact ([D12](D12-llm-fact-extraction.md)) carries its own complete copy of the text that generated it, so 1 digest that yields N facts writes the same source text N times, not 1 time with N facts pointing to it.

**Decision:** implement the path that [A7](A7-source-content-duplication.md) already sketched — a separate "source document", with facts referencing it by hash instead of copying the text — confirmed with the maintainer before touching anything (it affects [D9](D9-scope-domain-schema-four-axes.md)): `internal/store/sourceblob.go` adds a `sourceblobs.json` sidecar (the same atomic tmp+rename write discipline as `index.json`/`telemetry.json`) indexed by `sha256(text)`. Two functions in `store.go` bridge to the existing API contract without changing anything visible from outside:
- `internalizeMetadata` runs before any persistence (`addOne`, `Update`): if `metadata.source_content` (raw text) is present, it writes it to the blob store (automatic dedup — the same hash is never rewritten) and replaces the key with `metadata.source_content_ref` (the hash) before touching `s.index`/chromem-go.
- `externalizeEntry`/`externalizeEntries` run on every public output (`Get`, `Search`, `Recent`, `Add`, `Update`): they resolve `source_content_ref` back into the full text under `source_content`, as it always was. `docs/api-contract.md`, the WebUI (`EntryDetailPage.tsx`, "Extracted from:") and the `SessionStart` hook ([D17](D17-sessionstart-memory-injection.md), which only checks the presence of the key) do not change a line — the internal schema changed, the public contract did not.

`retroextract.go` (`pendingExtractionCandidates`) now checks for the presence of `source_content_ref` instead of `source_content` — the same signal as always ("this entry has already gone through extraction"), only the internal key changed.

**Existing data migrated, not just from now on:** the 220 entries already written (most of the current 7MB) had the real duplication — leaving things as they were would only help new facts. `internal/store/migrate.go` (`MigrateSourceContentBlobs`) runs on every boot of `m3m0s serve` (`cmd/m3m0s/serve.go`, right after `store.New`), idempotent: only entries that still carry raw `source_content` are touched, and once migrated an entry never shows up as a candidate again. It reuses the already-computed embedding (`chromem-go Collection.GetByID`) instead of calling the embeddings provider again — only the metadata changes, the `Content` (and therefore the correct embedding for it) stays the same; `chromem-go.AddDocument` does not recompute when it receives an `Embedding` already filled in (confirmed by reading the lib's `collection.go`), so the migration spends no new network calls.

**Out of scope:** garbage collection of orphaned blobs (when a dedup overwrites `source_content_ref` with a new hash, or an entry is deleted, the old blob stays in `sourceblobs.json` with no entry pointing at it) — not implemented now; the residue is orders of magnitude smaller than the N-per-fact duplication that this decision already eliminates, and it overlaps with [A9](A9-old-memory-compression.md) (compression of old memories, not yet decided) enough that it is not worth solving both at once without talking to the maintainer. Refcounting on the blobs is also left out for the same reason.
