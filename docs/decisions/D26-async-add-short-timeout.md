# D26 — Async add with a short timeout (`POST /memories` stops blocking the caller for seconds)

**Status:** Accepted

**Context:** the maintainer wants to support a future feature of "automatic memory ingestion as the user sends messages" — each user message would become a `memory_add` fired in the background, without the user noticing. Today `POST /api/v1/memories` (`internal/httpapi/server.go:handleAdd` → `internal/store/store.go:Add`) is 100% synchronous: the HTTP request stays blocked until the LLM fact-extraction pipeline finishes ([D12](D12-llm-fact-extraction.md)/[D18](D18-chunked-fact-extraction.md)/[D19](D19-forced-json-retry.md)/[D20](D20-disable-extraction-model-reasoning.md)) — even with the per-chunk parallelization of [D18](D18-chunked-fact-extraction.md)/[D19](D19-forced-json-retry.md), the budget is up to 25s per chunk (`extractionChunkBudget`). Blocking the caller for several seconds on every message is unacceptable in that scenario: the goal is for ingestion to happen imperceptibly, not to turn into a progress bar.

**Design:** `POST /api/v1/memories` gets a short, configurable wait timeout (`-add-sync-timeout`/`M3M0S_ADD_SYNC_TIMEOUT`, `cmd/m3m0s/serve.go`, default `300ms`). The handler always fires `store.Add` in its own goroutine — the difference is only how long it waits for it before answering:
- Finished within the timeout → answers **200** with the usual `AddResponse` (plus an additive field `status: "completed"`, `omitempty`, which breaks no client that already ignores unknown fields).
- Did not finish → answers **202 Accepted** with `{ operationId, status: "pending" }` (`apitypes.AddPendingResponse`) and the goroutine keeps running behind the scenes, writing the final result to an in-memory tracker (`internal/httpapi/pendingadd.go`, `pendingAddTracker`) — pollable at **`GET /api/v1/memories/pending/:id`** (`apitypes.PendingAddResponse`: `status` pending/completed/failed, `result` only when completed, `error` only when failed; 404 for an unknown or already-expired ID).
- `-add-sync-timeout <= 0` is the escape hatch: it disables the asynchronous path entirely, always waits for the Add to really finish — behavior identical to pre-D26, useful for whoever prefers the old semantics (e.g. a script that already handles the synchronous response and does not want to deal with polling).

**`context.Background()`, never `r.Context()`, in the Add goroutine — the critical detail of this design:** if extraction ran under the HTTP request's context, it would be cancelled the instant the handler answers (200 or 202) and the connection closes — precisely the case the asynchronous path exists to support. An in-flight Add has to survive the request that triggered it.

**Ephemeral tracker, on purpose:** `pendingAddTracker` lives only in process memory — it is not persisted in any JSON sidecar (unlike `index.json`/`sourceblobs.json`/`apikeys.json`, which follow the tmp+rename discipline). If the process restarts with an Add in flight, that specific operation simply disappears — the same practical result as a synchronous Add interrupted by a crash today, so it is not a durability regression, just an explicit characteristic of the design. The result of an already-finished operation (completed/failed) stays available for polling for a short TTL (`pendingAddTTL = 15min`, `time.AfterFunc` removes it from the map after that) — it avoids unbounded map growth in a long-lived process without needing a separate cleanup job ([D16](D16-in-process-jobs.md)).

**Go client transparent to polling:** `internal/client.Client.Add` keeps the exact public signature (`Add(ctx, req) (apitypes.AddResponse, error)`) — the CLI, `m3m0s watch`, `m3m0s mcp` and `internal/selfindex` do not need to change anything. Internally: 200 decodes directly (the usual path); 202 decodes `AddPendingResponse` and enters a polling loop on `GET /memories/pending/:id` every 200ms until `status != "pending"`, respecting the received `ctx` (cancellation/timeout from the caller interrupts the loop immediately). The polling imposes no total time ceiling of its own beyond the `ctx` — each individual HTTP call (the initial POST, each poll GET) already expires via the internal `http.Client` timeout (30s CLI/MCP, 120s `m3m0s watch`, [D24](D24-watch-on-own-repo.md)), so an Add that never finishes on the server makes the client fail by transport timeout on the next poll call, not hang in an infinite loop. Since the method needs the raw HTTP status code to decide which shape to decode (something the client's generic `do()` deliberately did not expose for the other methods), `Add` uses a new internal variant (`doRaw`) just for itself — `do()` stays untouched for the rest of the client.

**Accepted trade-off:** a pending operation does not survive a process restart (see "Ephemeral tracker" above) — acceptable because the use case that motivated this decision (automatic background ingestion) already does not expect synchronous confirmation from the user; if the process goes down midway, the worst case is the same message having to be resent, no different from any other infra failure.
