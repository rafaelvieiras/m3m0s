# D13 — Scope of the admin WebUI (Phase 5)

**Status:** Accepted

**Context:** the maintainer asked whether any UI exists today — the answer was no: the 3 access channels (CLI, HTTP API, MCP) have no visual surface, and the React WebUI planned in [D2](D2-stack-go-core-typescript-only-where-required.md) (reusing the legacy `memory-server` WebUI) never became a checklist item in any phase of the plan — it only existed as a stack decision, never as a deliverable. The old WebUI code was checked: 3 tabs (Search/Recent/Add), no auth (the old `memory-server` had none), filtering only by `project` (a field that no longer exists in the 4-axis schema, [D9](D9-scope-domain-schema-four-axes.md)), no delete, and no view of fact extraction (which did not even exist at the time). The maintainer confirmed that the old UI "was not very usable" — this is not a 1:1 port, it is a redesign.

**Decision, in 3 parts:**
1. **Functional scope of v1 — all 4 proposed items, including the largest one:** search/browsing with filters over the 4 schema axes ([D9](D9-scope-domain-schema-four-axes.md)) + a stats panel; extraction validation (shows the original input and the N atomic facts generated by the Phase 4/[D12](D12-llm-fact-extraction.md) extraction before confirming); manual delete from the UI (uses `DELETE /memories/:id`, which already exists — [D11](D11-watch-mechanism.md)); and editing an existing entry (a new `PUT`/`PATCH /memories/:id` endpoint, which does not exist in the contract today — the largest scope of the four, it must go into `docs/api-contract.md` before coding).
2. **Authentication: a login screen, paste the API key once, store it in `localStorage`, send it as `Authorization: Bearer` on every call.** The same auth model the backend already has ([D6](D6-getengram-analysis.md)/Phase 1) — zero server changes. The alternatives of embedding the key in the build (exposes the key in any served JS bundle) and of disabling auth for the local origin (it would open an exception to the Phase 1 auth rule with no real need) were rejected.
3. **Retroactive traceability of extraction: yes — each extracted fact now carries `metadata.source_content`** (the original text that generated it). A schema/backend change in `internal/store.Add` (Phase 4/[D12](D12-llm-fact-extraction.md)), not just the front end — it lets the UI show "extracted from: ..." at any time after the add, not only at the moment of the call (the `POST /memories` response already shows this immediately, but it is lost afterwards if not persisted in some field).

**Why:** the maintainer raised the question because today there is no way to visually validate what fact extraction (Phase 4, just implemented) is writing, nor to administer memory without reading raw JSON or using the CLI — a real gap for the goal of trusting the automatic pipeline. Scope closed with the maintainer on 15 Jul 2026 via structured questions (the same discipline as [D9](D9-scope-domain-schema-four-axes.md)/[D11](D11-watch-mechanism.md)/[D12](D12-llm-fact-extraction.md)), covering the 3 axes that blocked starting to code: what to build, how to authenticate, and whether a new provenance field is needed.

**Later elaboration (contract, 16 Jul 2026):** the complete design of item 1 (editing) and item 3 (`source_content`) was closed in `docs/api-contract.md` — `memory_update` becomes `PATCH /memories/:id`, a first-class operation on all 3 surfaces (HTTP+MCP+CLI, unlike `memory_delete`, which stays HTTP-only by design of [D11](D11-watch-mechanism.md)), without running extraction ([D12](D12-llm-fact-extraction.md)) or dedup again — it is a manual, deliberate overwrite of 1 entry, not raw input. Two details that D13 had left implicit: (a) the stats panel (the "understand how it is working" item) gains an `extraction: {enabled, model}` field in `GET /stats`, mirroring `M3M0S_EXTRACT_API_KEY`/`M3M0S_EXTRACT_MODEL`; (b) when an extracted fact is deduplicated against an existing entry, `metadata.source_content` now reflects the **most recent** fact (it overwrites the old one), by the same logic that already applies to the rest of the dedup merge (`content`/`tags`/`metadata`: the most recent wins, the original is never preserved).

**Later elaboration (frontend stack, 16 Jul 2026):** the maintainer closed the WebUI's technical stack before coding — Vite + React ([D2](D2-stack-go-core-typescript-only-where-required.md)) remains the base, plus: Tailwind (styling), shadcn/ui (components), TanStack Query (cache/fetch against `serve`'s HTTP API), TanStack Router (routes), TanStack Form (forms — add/edit screens), TanStack Virtual (list virtualization — search/recent may have many results), Zod (schema validation, including mirroring the formats of `docs/api-contract.md` on the client), and lazy loading of routes/components via `React.lazy`/`import()`. It does not change any functional scope already closed above — it is only the choice of libraries for the Phase 5 implementation task (`docs/implementation-plan.md`).

**Architecture correction (embedding + API prefix, 16 Jul 2026):** when trying to access the finished WebUI, the maintainer pointed out that the "separate build, served separately" design (the original text of the `webui/` item in the repo structure section of `AGENTS.md`) was wrong — it required starting two processes by hand (`m3m0s serve` + `npm run dev`) for a simple administrative task. **Revision:** the *build* remains separate (`npm run build` generates `webui/dist`, the Node pipeline stays outside the Go binary — [D2](D2-stack-go-core-typescript-only-where-required.md) does not change), but the *serving* becomes embedded: `m3m0s serve` embeds `webui/dist` via `go:embed` (package `webui`, new `embed.go`) and serves both the API and the static assets in the same process/port — a single binary, a single deploy artifact, aligned with [D4](D4-host-docker-on-desktop-first.md) (a Raspberry Pi: no Node/nginx running separately on the final host). Direct consequence: every HTTP API route now lives under `/api/v1/*` (versioning + an unambiguous namespace separation between the API and the static assets served at `/`); `GET /health` stays outside the prefix, by convention (infra/orchestrator probes expect that fixed, unversioned path). Dev keeps hot-reload via `npm run dev` (Vite), but now with a proxy of `/api/v1` to `m3m0s serve` — the WebUI's HTTP client now uses a relative path (`/api/v1/...`), with no need for `VITE_M3M0S_URL` in the common case (it only serves as an override to point at a remote `serve`, if needed). Implementation detail: since `go:embed` fails at build time if the referenced directory does not exist, `webui/dist/` gets a minimal placeholder committed to the repo (replaced by the real output as soon as `npm run build` runs) — it prevents a fresh clone from breaking `go build` by depending on a Node artifact not yet generated.
