# D27 — In-process job visibility and control in the WebUI (history, manual run, runtime interval)

**Status:** Accepted

**Context:** the maintainer asked for a new page in the admin WebUI for the jobs system (`internal/jobs`, [D16](D16-in-process-jobs.md)) — today only `forget-sweep` ([D22](D22-memory-layers-automatic-forgetting.md)) and `retroactive-extraction` ([D12](D12-llm-fact-extraction.md)/[D16](D16-in-process-jobs.md)), each with a fixed interval defined only by flag/env at the boot of `m3m0s serve`. None of the surfaces (HTTP/MCP/CLI/WebUI) gave any visibility once the server is up: there was no way to see when a job last ran, what happened, trigger it manually, nor change the interval without restarting the process with a different flag. An explicit request for a **generic** UI: it iterates over the list of jobs the API returns, not hardcoded for the name of a specific job — any future job registered in the scheduler shows up for free, without changing the page.

**Backend — `internal/jobs/scheduler.go`:** `Job.Run` changes from `func(ctx) error` to `func(ctx) (summary string, err error)` — `summary` is a short, human-readable sentence (e.g. "15 memory(ies) processed"; empty when there is nothing relevant to report in this run), reusing the messages the 2 existing jobs already logged via `log.Printf` in `cmd/m3m0s/serve.go`. `scheduledJob` gains a `history []JobRun` (most recent first, capped at the last `historyLimit = 20` runs) protected by the same `Scheduler.mu` that already protected `nextRun` — no new mutex, the same concurrency discipline as before D27. `Scheduler.Status() []JobStatus` returns a snapshot of all jobs (name, interval, `running`, `nextRun`, last run, history). `Scheduler.TriggerNow(name)` fires a job outside the normal cycle — the same overlap protection that `runDue` already had (`atomic.Bool` via `CompareAndSwap`, not separate `Load`+`Store`: it closes a race window that existed even before D27 between the normal tick and a concurrent manual trigger), `ErrJobAlreadyRunning` instead of queueing or running in parallel. `Scheduler.SetInterval(name, interval)` changes the `Interval` at runtime and recalculates `nextRun` from now — a perceptible effect without needing "run now" nor restarting the process. `ErrJobNotFound`/`ErrJobAlreadyRunning` are sentinels (`errors.Is`), so `internal/httpapi` can translate them into the right HTTP code without comparing strings.

**Backend — persistence of the custom interval:** `internal/jobs/persist.go` — a `<dataDir>/jobs-config.json` sidecar (`map[string]int64`, job name → seconds; the same tmp+rename discipline as `persistIndexLocked`/`persistTelemetryLocked` in `internal/store/store.go`) via `LoadIntervals`/`SaveIntervals`. `SaveIntervals` always writes the full map (never a partial merge) — the merge happens on the caller's side. `cmd/m3m0s/serve.go` loads this sidecar at boot and uses a saved override, when present, in place of the flag/env value when registering `forget-sweep`/`retroactive-extraction` (no override: identical behavior to before D27). The HTTP handler of `PATCH /api/v1/jobs/:name` (below) persists the change again after each successful `SetInterval` — it loads the current overrides, applies the new one, writes everything back.

**Backend — HTTP (`internal/httpapi/jobs.go` + routes in `internal/httpapi/server.go`):** `GET /api/v1/jobs` lists all with history included (`jobsSched == nil` — the same pattern as `chat == nil` disabling `POST /api/v1/chat`, [D23](D23-webui-floating-llm-chat.md) — returns an empty list instead of an error, useful for tests that do not care about jobs); `POST /api/v1/jobs/:name/run` calls `TriggerNow` (`404 job_not_found`/`409 job_already_running`); `PATCH /api/v1/jobs/:name` with body `{"intervalSeconds": N}` calls `SetInterval` + persists (`400 invalid_interval` if `N <= 0`, `404 job_not_found`). New types in `internal/apitypes/types.go`: `JobRun`/`JobStatus`/`JobsListResponse`/`JobRunResponse`/`JobIntervalRequest` — always integer seconds on the wire (`intervalSeconds`/`durationMs`), never a serialized `time.Duration`, which is the format the WebUI speaks. `Server.New` gains 2 new parameters (`jobsSched *jobs.Scheduler`, `jobsConfigPath string`), both optional (nil/empty disables the 3 routes/the persistence respectively).

**Frontend — generic `/jobs` page:** `webui/src/pages/JobsPage.tsx` iterates `data.jobs` (never a hardcoded job name) — each job becomes a `Card` with name, running/idle badge, interval editor (numeric `Input` + `Select` of unit seconds/minutes/hours, converted to seconds before the PATCH), a summary of the last run (locale-formatted date/time, duration, success/error badge, summary/error message) and a compact `Table` of recent history. `useJobs()` (`webui/src/hooks/useJobsApi.ts`) uses `refetchInterval: 5000` — with no SSE/websocket infrastructure in the project ([D23](D23-webui-floating-llm-chat.md)), short polling is the only way to reflect "running now"/completion without a manual F5. The interval editor keeps local state via a lazily-initialized `useState`, set once from the job's current value (not on every polling refetch — otherwise it would overwrite an edit in progress in the middle of typing every 5s). The route is registered in `webui/src/routes/jobs.tsx` (the same `lazyRouteComponent` pattern as `routes/stats.tsx`) and in `AppShell` (a `ListChecks` icon, lucide-react).

**Out of scope:** cancelling a run in progress (the `Job.Run` contract does not receive a way of being interrupted from outside — only the already-existing `ctx`, which nobody cancels today); any MCP/CLI surface for jobs (WebUI-only in this v1, the same deliberately restricted scope as [D23](D23-webui-floating-llm-chat.md) — the CLI/external agents have no operational need to trigger jobs manually today).
