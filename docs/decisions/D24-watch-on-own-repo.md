# D24 — `m3m0s watch` pointed at the project's own repo + per-chunk/file failure resilience

**Status:** Accepted

**Context:** after [D23](D23-webui-floating-llm-chat.md), the maintainer asked the WebUI chat "which model are you using" and it could not answer — m3m0s's memory had never been fed the project's own documentation (`AGENTS.md`/`docs/**/*.md`), so the chat's RAG had nothing to retrieve about its own infrastructure. `m3m0s watch <dir>` (Phase 2, [D11](D11-watch-mechanism.md)) has existed for exactly this since 15 Jul 2026, but it had never been pointed at the real project root (only leftover state from test runs remained in `~/.m3m0s/watch/`).

**Activation:** a `systemd --user` service (`~/.config/systemd/user/m3m0s-watch.service`, `WantedBy=default.target`, `Restart=on-failure`) running `m3m0s watch /path/to/repo --domain codigo:m3m0s` — it starts at login and automatically reindexes any change to `AGENTS.md`/`docs/**/*.md` via fsnotify from then on. No new hardware/process: it reuses the already-compiled local Go binary (`~/go/bin/m3m0s`) talking to the `m3m0s serve` already running in Docker (`M3M0S_URL`/`M3M0S_API_KEY` from `~/.m3m0s/hook.env`, the same credential already used by the Claude Code hook, [D14](D14-claude-code-hook-auto-capture.md)).

**Bug found when turning it on for the first time:** the initial scan (`Sync`) crash-looped every ~1-2min — the `POST /api/v1/memories` of an `AGENTS.md` chunk blew the client's HTTP timeout (30s, [D17](D17-sessionstart-memory-injection.md)) while the server was still processing the synchronous fact extraction ([D12](D12-llm-fact-extraction.md)/[D18](D18-chunked-fact-extraction.md)/[D19](D19-forced-json-retry.md)) of the chunk. `ReconcileFile` propagated that error upward until `Run` returned non-zero, systemd restarted the process, and since `state.Set` was only called at the end (after ALL the file's chunks had been added successfully), each crash threw away the progress of the entire file — reprocessing from scratch and spending extraction tokens again on every attempt, never finishing.

**Fix — two independent adjustments, the same rationale as [D18](D18-chunked-fact-extraction.md) (isolate failure, do not let 1 slow piece take down the rest):**
1. `internal/client`: `NewWithTimeout`/`NewFromEnvWithTimeout` — `m3m0s watch` (`cmd/m3m0s/watch.go`) now uses 120s instead of the 30s default. The scope of the increase is only the watch's client — CLI/MCP keep the 30s designed for interactive use ([D17](D17-sessionstart-memory-injection.md)); batch indexing during the initial scan is not a synchronous user wait on screen.
2. `internal/watch/watch.go`: `ReconcileFile` no longer aborts on the first chunk that fails — it logs and continues to the next chunks of the same file; it only marks the file as synchronized (`state.Set`, advances the hash) if **all** chunks went well, otherwise the next scan retries the whole file (the old behavior, but now without crashing the process to get there). `Sync` no longer aborts the entire tree on the first problematic file — each `ReconcileFile`/`ReconcileDelete` error becomes a log and the scan moves on to the next files/directories.

**Verified in production:** before the fix, the service crashed and restarted repeatedly without ever finishing indexing even `AGENTS.md` alone. After the rebuild, it ran ~10 minutes uninterrupted with no crash (`journalctl` with no `Main process exited` since the restart), `GET /api/v1/stats.count` rose monotonically and stably (312 → 400+ memories) while processing `AGENTS.md` and every `docs/*.md`, and a search for "which model does the chat use" started returning real chunks of the project's own documentation (including the [D23](D23-webui-floating-llm-chat.md) content about `internal/chat` and the default extraction model).

**Out of scope:** automatic retry of the chunk that failed within the same run (left for the next scan/process restart); a periodic resync mechanism independent of fsnotify (today there is only the initial `Sync` + file events — if a file gets stuck on a persistent failure, only a `systemctl restart m3m0s-watch` forces a new full attempt).
