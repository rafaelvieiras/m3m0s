# D23 — Floating LLM chat in the WebUI (ask via RAG, save via tool-calling)

**Status:** Accepted

**Context:** the maintainer asked, on 17 Jul 2026, for a chat inside the WebUI able to answer questions about memory and to insert new memories with the help of an LLM — asking should not require any dedicated command (the assistant searches by itself), while saving should go through an explicitly configured "skill". An explicit UX request: a floating panel on the right side of the screen, expandable/closable, persistent across route changes (not across reloads), with a `/clean` command and command autocomplete.

**Chosen architecture — two capabilities, a single call:**

- **Ask (automatic RAG, no tool):** every `POST /api/v1/chat` extracts the last user message and runs `store.Search` against it (best-effort — a search failure becomes a log, never takes the response down), injecting the 5 most relevant results into the system prompt via `apitypes.BuildContextBlock` — the same helper already used by the `SessionStart` hook ([D17](D17-sessionstart-memory-injection.md)), reused here instead of duplicated. The LLM answers based on that context without needing any function-calling: "asking" is always free/automatic, as requested.
- **Save (tool-calling):** a single tool, `add_memory` (`content`, with optional `domain`, `tags`), exposed to the LLM via `tools`/`tool_choice: "auto"` in the OpenAI-compatible format (supported by OpenRouter, the same provider already used by fact extraction, [D12](D12-llm-fact-extraction.md)). The system prompt explicitly instructs the model to only call the tool when the user asks to remember/save/store something — never in response to an ordinary question. The `source` of the created memory is always fixed at `"webui-chat"`, never controlled by the LLM (it prevents a prompt injection from swapping the provenance).

**New package `internal/chat`:** an OpenAI-compatible client (OpenRouter) with tool-calling support — deliberately decoupled from `internal/extract` (it does not import that package, it duplicates `DefaultBaseURL`/`DefaultModel` as literals) and from `internal/store` (it only speaks chat completions, it does not know what an `Entry` is). The same rationale as [D20](D20-disable-extraction-model-reasoning.md): `reasoning: {enabled: false}` always on — the goal is a fast conversational answer, not an invisible reasoning step. Unlike `internal/extract.Extract` ([D19](D19-forced-json-retry.md)), it does **not** force `response_format: json_object` — here the response is natural-language text, not an array/object of facts.

**Tool-calling orchestration in `internal/httpapi/chat.go`, not in the `chat` package:** `chat.Client.Complete` makes 1 call and returns the raw message (text and/or `tool_calls`); the handler decides what to do with a `tool_calls` (execute `store.Add`, build the `role: tool` result message, call `Complete` again) — at most `chatToolRounds = 2` rounds, a total timeout of 45s per HTTP request (more generous than the client's 30s per call, since there may be 2 calls in sequence). It keeps the `chat` package thin and testable in isolation, and leaves the policy ("when add_memory is allowed", "how many rounds") in the place that already knows the domain (`internal/store`).

**Configuration — key shared with extraction for convenience:** `-chat-key`/`M3M0S_CHAT_API_KEY` takes priority; if absent, it falls back to the same value already configured in `-extract-key`/`M3M0S_EXTRACT_API_KEY` — whoever already turned on fact extraction ([D12](D12-llm-fact-extraction.md)) gets the chat "for free" with the same OpenRouter key, without duplicating an environment variable. With no key resolved in either, `POST /api/v1/chat` degrades gracefully to 503 (the same degradation pattern as extraction when disabled) — never 500.

**Scope deliberately restricted to the WebUI:** unlike `forget-sweep`/`restore` ([D22](D22-memory-layers-automatic-forgetting.md), which gained all 3 surfaces HTTP/MCP/CLI), the chat only exists as `POST /api/v1/chat` — there is no MCP tool nor CLI subcommand. It is a conversational UX feature of the WebUI, not a structured operation that the CLI/external agents need to call directly (they already have native `memory_add`/`memory_search`, more direct than going through an intermediate LLM).

**Frontend (`webui/`):** `ChatWidget` (`components/chat/ChatWidget.tsx`) mounts only once in `AppShell.tsx`, as a sibling of `<main>` — outside the `<Outlet/>`, so it survives route changes without remounting (the `_authed` layout that wraps `AppShell` already does not remount between child routes, [D13](D13-webui-admin-scope.md)). The conversation state lives in the component's own local `useState` — it persists while the panel opens/closes (it only toggles visibility, it does not unmount), but it does not survive a page reload, on purpose (no `localStorage` — a deliberate decision to keep the scope simple in this first version). The `/clean` command (`components/chat/chat-commands.ts`) runs 100% locally, without calling the API. Autocomplete: a dropdown filters `CHAT_COMMANDS` by prefix while the user types `/something` with no space yet, keyboard-navigable (arrows/Tab/Enter/Esc). When the response carries a non-empty `toolCalls` (a memory was saved), the `useChatMessage` hook invalidates the TanStack Query caches of `recent`/`search`/`stats` — the rest of the UI reflects the new memory without a manual reload.

**Out of scope for this first version:** response streaming (the project has no SSE/chunked infrastructure in `internal/httpapi` — the response is a synchronous JSON; the UX is acceptable with a "typing…" indicator, revisit if latency bothers in practice); conversation persistence across reloads; syncing the chat's `domain` with the current page's filter (the WebUI has no concept today of a "current domain" shared across routes — each screen keeps its own local filter); additional tools beyond `add_memory` (search is already automatic via RAG, it does not need a tool for that).
