# D12 — LLM fact extraction (Phase 4)

**Status:** Accepted

**Context:** Phase 3 exposed in practice the limit of raw text — see the auto-capture discussion of 15 Jul 2026 (`pi` does not write memory on its own because `memory_add` is *pull*: the model has to decide to call it). Before touching automatic capture, the maintainer asked to settle how fact extraction itself should work, based on how Claude-Mem/Mem0/Cognee/Zep already solve it — not on options made up on the spot. Research is in the original memory-system comparison (14 Jul 2026) and in the initial architecture analysis (15 Jul 2026, already cited in `AGENTS.md`).

**Decision, in 5 parts:**
1. **Scope: `memory_add` and `m3m0s watch`, both — not just one.** Every competitor researched extracts at every entry point, not selectively: Mem0 has `infer=True` on every `add()`; Zep auto-extracts both in `graph.add()` and in `thread.add_messages()`; the project's own original analysis (Phase 1, recommendation 1) already said "`memory_add` calls DeepSeek Flash" — not "only the watch". Applying it only to `watch` (the initial suggestion) matches no real precedent. Enabled/disabled at the server level by the presence of `M3M0S_EXTRACT_API_KEY` (the same toggle pattern that `-openai-base` already uses for embeddings) — no per-request or per-domain flag in this phase; if some domain does not benefit (e.g. `codigo:*` with already-structured content), re-evaluate later with real quality data, not by guessing now.
2. **Output: N independent atomic facts per input, each becoming its own `Entry`.** Mem0 and the original analysis agree on this ("each fact must be self-contained... store each fact as a separate memory"). Claude-Mem does something richer (one record per observation with `title`/`subtitle`/`narrative`/`facts`/`concepts`/`type`) — deliberately **not adopted now**: it is a larger schema redesign, left as an idea for a future iteration if the simple list of atomic facts proves insufficient. Each fact inherits `domain`/`source`/`agent`/`tags`/`metadata` (provenance) from the original input and goes through the existing dedup pipeline (`DedupSimilarityThreshold`) individually — a repeated fact does not become a duplicate entry just because the source text changed shape. **API consequence (breaking, no shim):** `AddResponse` stops being `{entry, deduped}` (singular) and becomes `{entries: [{entry, deduped}, ...], extracted: bool}` — Phases 1/2 never had real external use outside this project, so it is a direct swap, with no route versioning.
3. **Provider: OpenRouter, not OpenAI.** The old `memory.ts` already validated this pairing for the same kind of task (session summary via "DeepSeek V4 Flash/OpenRouter", see the architecture analysis §1) — it is cheaper than keeping everything on OpenAI, and avoids putting more load on the same account used for embeddings. Default model is configurable (`M3M0S_EXTRACT_MODEL`, initial guess `deepseek/deepseek-v4-flash` or the cheapest available — adjustable without changing code), with a new client in `internal/extract` (manual chat completions over OpenRouter's OpenAI-compatible API, no new dependency in `go.mod`, in the same spirit as the hand-written `**` matcher from Phase 2). The credential (`OPENROUTER_API_KEY`) was provided directly by the maintainer in the conversation, not extracted from `pi`'s auth file — an automated attempt to read that file was denied twice by the permission classifier of that session (even with the maintainer's generic authorization to "fetch pi's credential"); documented here so the next session does not repeat the attempt.
4. **Secret redaction happens both BEFORE and AFTER extraction.** Until Phase 3, only the embedded text left the process (to OpenAI). From now on, the raw text also leaves the process to a third-party provider (OpenRouter) before becoming a fact — so `internal/redact` ([D6](D6-getengram-analysis.md)) runs on the raw content *before* it is sent to the extractor, and again on each extracted fact *before* embedding/storing (defense in depth: the extractor should not invent new secrets, but it costs nothing to make sure).
5. **Fallback: if extraction fails (timeout, error, unparseable JSON), insert the original content (already redacted) as 1 raw entry — the same as the pre-Phase-4 behavior — and log the error.** A memory is never silently lost because of a failure in the extraction provider.

**Out of scope for this decision (D12 does not cover):** the auto-capture hook in `pi` (or any other tool) that would trigger `memory_add` automatically — the maintainer explicitly decided to postpone this until the isolated extraction is validated (15 Jul 2026). Also out: re-evaluating [A6](A6-embeddings-provider.md) (embeddings provider) — the research in this decision was only about fact extraction, not about replacing `text-embedding-3-small`.
